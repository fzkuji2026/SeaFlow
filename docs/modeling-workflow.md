# Decision-modeling contract

The optimizer separates segmentation, estimation, and action selection. A
negative game never creates a new strategy branch by itself.

## 1. Canonical labels

Every decision has two identifiers generated by `glee_agent.segments`:

- `scenario_id`: decision-time static variables that define the same task and
  role. Hidden opponent values are recorded as `hidden`, never read from the
  completed replay.
- `state_id`: `scenario_id` plus action type, current procedure, observed
  opponent style, and an evidence-count band.

The parent order is fixed:

1. exact `state_id`;
2. exact scenario + action + procedure;
3. exact scenario + action;
4. same visible scenario with the message-availability flag pooled + action +
   procedure;
5. the same pooled scenario + action;
6. existing deterministic workflow.

Message pooling is the only static-variable relaxation because chronological
ablation found no stable message-availability effect on numeric action value.
There is no global-model action fallback. Global aggregates are diagnostics only.
Pooled-message models normally estimate diagnostics only. A response policy may
act from a pooled-message parent only with at least eight effective games,
three chronological-holdout improvements, zero holdout regressions, and
positive train and holdout gain. Offer actions still require the same procedure
parent.

## 2. Indicator ownership

| Family | Static task indicators | Dynamic opponent indicators | Estimated targets | Action comparison |
| --- | --- | --- | --- | --- |
| Bargaining | role, own/visible opponent delta, horizon, information, messages | current/best share, rejected offers, samples, style | offer acceptance, value after rejected offer, value after rejecting an incoming offer | discounted accept/offer value versus continuation value |
| Negotiation | role, own/visible opponent multiplier, horizon, information, messages | current/best price, concession, rejected offers, samples, style, fitted ZOPA probability | price acceptance, value after rejected price, and hidden-value overlap | own profit of each price versus its fitted continuation |
| Persuasion buyer | prior, values/price, seller knowledge, message type, myopia | signal, revealed quality, seller reliability | high-quality posterior | buy EV versus zero |
| Persuasion seller | same persuasion configuration | yes/no response counts and buyer style | yes/no sale probability and future trust cost | current sale probability plus remaining expected sales |

Money scale is logged but excluded from the task identifier because the games
are scale invariant and five-window ablation found no stable predictive gain.
Round number is not a category; models receive continuous progress.

`glee_agent.segments.MODEL_SCHEMA` is the executable registry for this table.
Each family must declare its indicators, estimated targets, candidate set,
objective, non-overridable constraints, and fallback. Adding a fitted cell may
change an estimate; it may not silently change the objective or legal candidate
space.

Each family also declares `strategy_map`. It is the required mapping from an
action type to the estimates it consumes, the candidate-value equation, and the
candidate set it may select. A strategy branch that cannot be represented by
this mapping is diagnostic-only until the registry and its validation are
updated together.

Bargaining responses apply one deterministic value-consistency constraint
before fitted estimates: accept when the discounted value available now is no
lower than the discounted value of the workflow's own next planned offer even
if that next offer were accepted immediately. This compares state-dependent
values rather than round numbers or fixed shares.

After fitted estimates, a shared response-value model may override the named
procedure only when visible behavior supplies enough evidence. It compares the
discounted offer available now with both the rejection-weighted value of the
next own offer and an optimistic projection of future opponent offers. The
projection uses observed concessions, opponent-boundary repetitions, rejected
own offers, and the platform horizon. The trace records both candidate values,
the evidence gate, the uncertainty guard, and the machine-readable reason.
Named procedures remain fallbacks when the evidence gate does not pass.

Replay reconstruction is part of the modeling contract. It must reproduce the
decision-time `valid_actions` schema, including the optional `message` field.
Otherwise `rules.parse()` will correctly infer that a nonempty schema without
`message` forbids messages and the offline segment will be mislabeled. Tests
must cover this invariant before any model is regenerated.

## 3. Evidence gate

A fitted cell may affect live play only when all conditions hold:

- enough effective games and both required outcomes are present;
- the same feature set improves the relevant metric in chronological holdout;
- the proposed policy improves normalized payoff on train and holdout;
- the nearest sibling cell does not show a material regression;
- the model has support for the candidate action;
- the predicted advantage exceeds the stored uncertainty guard.

Targets combined in one candidate-value equation must come from the same
parent key and be evaluated on that candidate's own feature vector. Mixing an
exact acceptance model with a pooled continuation model, or reusing the
fallback candidate's continuation value for another candidate, is invalid.

Otherwise the selector moves to the next parent. If no fitted parent passes,
the existing workflow decides.

Bargaining response policies additionally require transfer validation on a
separate agent and frozen deployment. Evaluation again uses only the first
triggered rejection per game. A policy is deployable only after at least three
external improvements, zero external regressions, and positive external gain;
artifacts generated before this metadata existed are diagnostic-only.

Outcome analysis separates two labels:

- `realized_regret`: accepting an earlier observed offer would have produced a
  higher payoff than the eventual trajectory. This is a valid counterfactual
  label, but it is not by itself an action rule because the decision-time
  continuation distribution was unknown.
- `avoidable`: the alternative is also supported by a policy that passed the
  chronological evidence gate, or terminal dominance removed continuation.

Response-policy evaluation selects the first triggered rejection in each game.
Later decisions from the same trajectory cannot be counted as independent
improvements because the game would already have ended after the first accept.

Offline fitting always names a chronological holdout boundary explicitly:

```bash
PYTHONPATH=vendor:. python scripts/fit_models.py --holdout-ts TIMESTAMP
```

## 4. Trace contract

Every analyzed action records:

- `scenario_id`, `state_id`, and selected parent level;
- feature values and effective sample count;
- all legal candidates;
- acceptance probability, immediate value, continuation value, expected value,
  and uncertainty for each candidate;
- training, chronological-holdout, and external-validation trigger counts,
  gains, improvements, and regressions for any fitted response policy;
- chosen action and a machine-readable reason.

This trace is the training record and the explanation. Strategy code does not
add prose explanations or per-game exception branches.
